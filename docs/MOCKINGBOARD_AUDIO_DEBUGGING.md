# Mockingboard audio and CPU pacing

The red CPU pace indicator reports that the emulator did not execute its target
number of CPU cycles in the processing interval. It does not measure browser
CPU utilization. Audio backpressure can produce this symptom even when synthesis
is fast and both AY chips are silent.

## Reproduced causes

At SYSTEM 10 fps, each CPU slice represents 100 ms. The previous browser sink
allowed only 60 ms of scheduled audio plus pending PCM. Once that limit was
reached, `getCpuSliceBudget()` returned zero and `runCpuTicks()` stopped the
slice. A controlled two-second run executed 643383 of 2043600 requested ticks
(31.48%) in both JS and WASM. The same run at 60 or 100 fps executed every tick.
Vertical-blank mode uses approximately 60 SYSTEM slices per second, explaining
why it avoids this mismatch.

A second reproduction froze AudioContext time in a non-running state. The
queue then never drained, and the old admission policy executed only 30669
ticks (1.50%) over two seconds. This can explain a near-total stall, but the
reported browser session's AudioContext state has not been observed.

The fix sizes the scheduling ceiling to one configured processing interval plus
startup lead and margin, with a minimum of 60 ms. A suspended, interrupted or
closed AudioContext clears stale presentation output and releases CPU admission;
AY numerical state continues advancing silently. On resume, fresh PCM is
scheduled. Chip clock, output sample rate and playback rate remain fixed.

At 10 fps this requires about 130 ms of normal presentation lead. Lower-latency
audio at low video refresh rates would require a separate CPU/audio processing
cadence. This patch covers the UI's supported 10–100 fps range and keeps the
numerical PCM FIFO bounded to 250 ms.

## Diagnose a running browser session

Until the fix is applied, use vertical-blank mode or SYSTEM 60 fps as a workaround.
Disabling Mockingboard playback also isolates the sink's admission policy while
leaving the card mounted.

Paste this in the browser console while the emulator is running normally:

```js
(async () => {
    const io = apple2plus.hwObj().io;
    const card = Object.values(io.slots)
        .map(slot => slot.peripheral)
        .find(peripheral => peripheral?.id?.PCODE === "MOCK");
    const sink = card?.devices.find(device => device.id?.DCODE === "MOCKAUDIO");
    const target = _o.CPU_TargetTicks_s;
    if (!sink || !(target > 0)) {
        console.log("Mount Mockingboard and select a running CPU speed first.");
        return;
    }
    const sample = () => ({
        wall: performance.now(), cpu: io.getClockTicks(),
        contextState: sink.audio?.state, contextTime: sink.audio?.currentTime,
        sink: sink.getStats(), ay: card.getAYDiagnostics()
    });
    const before = sample();
    await new Promise(resolve => setTimeout(resolve, 1000));
    const after = sample();
    console.log({
        cpuPercent: 100 * (after.cpu - before.cpu) /
            ((after.wall - before.wall) / 1000 * target),
        audioSeconds: after.contextTime - before.contextTime,
        before, after
    });
})();
```

Keep the tab visible and CPU speed unchanged during the sample. Around 100%
means the requested emulated CPU pace was achieved; it does not mean the browser
used 100% of a host CPU. A non-running context and unchanged `contextTime`
identify unavailable audio output. The patch adds `contextState`, `contextTime`,
`highWater_ms`, `cpuBudgetChecks` and `cpuBudgetBlocked` to sink diagnostics.
Repeated increases in `cpuBudgetBlocked` indicate audio admission is limiting
the CPU. Compare queued lead and pending AY frames before and after the sample.

If slowdown remains with a running context, collect a short browser CPU profile
with the card mounted and another with it unmounted, using the same disk and
processing settings. Also compare playback disabled and vertical-blank mode.
Check time spent in `runCpuTicks`, `getCpuSliceBudget`, audio flushing,
`ay_render_until` (WASM), and Ayumi processing (JS). Record browser version,
backend, SYSTEM fps, target CPU speed, context state and the console sample.
Avoid logging per-cycle activity, which can itself slow emulation.

After applying the patch, reload the updated scripts before comparing results.
Distribution bundles must be regenerated by the repository's normal build flow
if the page loads a bundled runtime.
