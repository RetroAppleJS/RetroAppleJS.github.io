# Phase 1.5A.3 / MB-04 — Mockingboard Timer 1 interrupt and HGR benchmark

**Status:** v0.1 executable candidate, **awaiting RetroAppleJS browser acceptance**. MB-01/MB-02/MB-03 were merged before this milestone and **are not changed by this package**.

## Objective

Replace the broad theoretical IRQ timing assumptions in the score encoding benchmark with an executable, bounded Apple II+ 6502 experiment. It measures three things in *emulated CPU cycles*:

1. The service interval inside an actual **Apple II ROM-dispatched IRQ handler** using two 6522 Timer 1 samples.
2. Variation in the timestamps of AY R8 writes generated by a periodic timer interrupt.
3. The reduction in **foreground HGR memory-write throughput** when the IRQ handler additionally updates R8.

This is a dedicated diagnostic, **not a resident production music player**. It does not decode `.aysb` / E1 input or install an IRQ across BASIC statements. Hardware-clock correctness on a real 6522 is not proven by RetroAppleJS alone.

## Runtime and memory

- **Source of truth:** `asm/AY_SCORE_TIMING_MB04.S`.
- **Load:** 616 bytes at `$6000–$6267`, with source-label entries at fixed offsets below.
- **Physical Mockingboard slot:** **PR#4**, with VIA 1 at `$C400–$C40F`.
- **Internal emulator slot index:** `SlotN = physical slot + 1`, hence SlotN 5 for PR#4; legacy `mockingboard-slot5-history.json` is correct for this setup.
- **RAM used by results:** `$6C00–$6CBF` (IRQ exit T1 low samples), `$6E00–$6EBF` (IRQ entry T1 low samples), `$6F02–$6F0D` (working state), `$6F10–$6F3F` (3 result records). Do not run with programs that own these addresses.
- **Graphics:** HGR page 1 `$2000–$3FFF` is actively modified by the two graphics modes.
- **ROM software IRQ vector:** `$03FE/$03FF`; previous vector saved/restored.
- **Monitor zero-page `$45`:** ROM IRQ dispatch overwrites it; the diagnostic restores it before returning to BASIC. No BASIC execution occurs with the diagnostic IRQ installed.
- **VIA resources:** Takes exclusive ownership of VIA1 T1, T2, ACR and AY channel A volume. Does not preserve any prior Timer 1 program, old VIA port state or prior AY mixer/volume settings. Run in a disposable emulator instance with no concurrent IRQ programs.

| BASIC entry | Operation | Timed IRQs | Foreground |
|---|---|---:|---|
| `CALL 24576` | Run A+B+C consecutively | 64 each | HGR, HGR, NOP |
| `CALL 24579` | MB-04A — count-only IRQ | 64 | HGR modifications |
| `CALL 24582` | MB-04B — IRQ volume DAC | 64 | HGR modifications |
| `CALL 24585` | MB-04C — IRQ volume DAC | 64 | simple NOP polling |
| `CALL 24588` | Emergency removal of our IRQ hook | — | no new run |

## Interrupt mechanism

- VIA1 Timer 1 is free-running (`ACR=$40`), with latch `$02FE` (766). The emulated 6522 has **N+2** interval from one reload to the next, so the intended period is **768 CPU cycles**, approximately 1.33 kHz at the emulator's 1,021,800 Hz nominal clock.
- The CPU has real IRQ assertion from `MockingboardR6522` through `hw.setIRQSource()` to the 6502. The 6502 enters the Apple II Monitor IRQ dispatcher, which saves interrupted A at `$45` and calls the soft vector at `$03FE`.
- The handler saves X/Y, checks VIA1 IFR bit 6, acknowledges T1 by reading `$C404`, records low-byte timer entry sample, optionally writes AY R8 with the **previously selected R8 address**, increments IRQ count, records a second T1 low-byte sample near exit, restores registers and executes `RTI`.
- Other IRQs are chained through the previous soft vector, with no acknowledgment of unrelated sources.
- The foreground runs until IRQ count reaches 64, masks interrupts, disables VIA1 T1 IER bit 6 and clears the pending T1 flag **before** restoring the previous IRQ vector and zero-page `$45`.

**Important limitation:** The two timer samples measure **only the instrumented interior of the handler** (read-to-read). They do not include the CPU's 7-cycle hardware IRQ entry, the Monitor ROM dispatch, or the final epilogue/RTI. Their difference is not the entire IRQ CPU cost; the HGR throughput comparison provides complementary evidence of foreground displacement.

The Timer 1 low byte wraps every 256 cycles; sampled interior time is required to remain below 256 cycles. If real samples look abnormal, retain the raw data; do not normalize away an unexpected wrap.

## Browser-only acceptance procedure

1. Use a **disposable Apple II/II+ RetroAppleJS session** with **Mockingboard installed in physical slot 4**. Do not run SID/Mockingboard background music simultaneously. Do not boot a program needing `$6000–$6267` or `$6C00–$6F3F`.
2. At the BASIC prompt type `NEW`, then paste the entire `build/AY_SCORE_TIMING_MB04_LOADER.bas`. This BASIC program includes the 616 bytes of 6502 code as decimal `DATA` and checks their checksum. **No Node, Python or external compiler is needed for acceptance.**
3. Open Mockingboard peripheral controls and start **History capture** (coffee-cup icon). Set buffer ≥64 KB. Start capture only after BASIC is loaded, to avoid unrelated AY setup writes.
4. Type `RUN`. The loader executes `HGR`, then `CALL 24576`, then `TEXT`; it prints the three result records and sampled interior IRQ cost/range. Typically the CPU work finishes quickly in emulated time. **It is not a real-time audio demo**; it generates 64 discrete volume updates in each volume mode.
5. Stop history capture in peripheral controls **without resetting the machine**.
6. Since the current Mockingboard toolbox may not display its JSON download button, open Chrome DevTools Console and run:

   ```javascript
   apple2plus.hwObj().io.SLOT2obj(5).downloadHistory();
   ```

   Internal `SlotN = 5` corresponds to **physical PR#4**, and the exported filename may be `mockingboard-slot5-history.json`. This metadata convention is intentional internal indexing, not a claim that the physical card is in PR#5.
7. Open `tools/AY_SCORE_MB04_VERIFY.html` directly in the browser and import the downloaded history JSON. Expect 137 AY writes, three passing register-write sequences, and a 768-cycle median IRQ R8 spacing. Export the verifier report JSON.
8. For HGR metrics, copy the BASIC output values `MODE`, `IRQ`, `HGR WRITES` and `T2 CYCLES` into the verifier's optional text box as CSV lines `mode,irqCount,hgrWrites,t2Cycles`, one per mode.
9. Upload the history JSON, verifier JSON and/or a screenshot of the BASIC result to ChatGPT for measured comparison with the synthetic predictions below.

If an IRQ leaves the machine unresponsive, `CALL 24588` is a best-effort emergency unhook **only if Applesoft is still executing**. Otherwise use a fresh disposable emulator instance. The binary controls a 6522 timer and installs an IRQ hook; running inside a busy BASIC or DOS program with another IRQ owner is unsafe.

## Result record format

Mode A record at `$6F10` (decimal 28432), B at `$6F20` (28448), C at `$6F30` (28464). Each has:

| Offset | Meaning |
|---:|---|
| +0 | `$A4` completion marker (decimal 164) |
| +1 | Mode 1 / 2 / 3 |
| +2 | IRQ count (64 expected) |
| +3, +4 | HGR writes, little-endian `uint16` |
| +5, +6 | Timer 2 elapsed CPU cycles, little-endian `uint16` |
| +7, +8 | Programmed Timer 1 latch `$02FE` (little-endian) |
| +9 | Error = 0 |

Three sets of raw samples are captured at:

| Mode | T1 sample near handler entry | T1 sample near handler exit |
|---|---|---|
| A | `$6E00..$6E3F` | `$6C00..$6C3F` |
| B | `$6E40..$6E7F` | `$6C40..$6C7F` |
| C | `$6E80..$6EBF` | `$6C80..$6CBF` |

The interior CPU-cycle estimate per IRQ is `((entryLow-exitLow) & 255)`. Entry phase offset is approximately `((254-entryLow) & 255)` cycles after Timer 1 reload; this is not an absolute CPU IRQ-latency measurement independently of the emulator timer semantics.

For a convenient BASIC spot-check after a combined run:

```basic
PRINT PEEK(28432),PEEK(28434),PEEK(28435)+256*PEEK(28436)
PRINT PEEK(28448),PEEK(28450),PEEK(28451)+256*PEEK(28452)
PRINT PEEK(28464),PEEK(28466),PEEK(28467)+256*PEEK(28468)
```

Each line prints completion marker 164, IRQ count 64, and graphics writes (zero for C).

## Predictions from the independent limited instruction simulator

The package includes a small limited 6502+VIA simulation solely to inspect control flow and generate synthetic reference traces. These numbers **must not be reported as measured RetroAppleJS data**:

| Mode | Predicted IRQs | Predicted HGR writes | Predicted T2 cycles | Predicted sampled handler interior |
|---|---:|---:|---:|---:|
| A | 64 | 1167 | 49322 | 36 cycles |
| B | 64 | 1119 | 49370 | 62 cycles |
| C | 64 | 0 | 49348 | 64 cycles |

These estimates predict a **roughly 4% throughput reduction** for HGR when the timer IRQ also writes AY R8, under the diagnostic's exact memory-access and instrumentation path. They do not generalize to arbitrary HGR sprite engines or to real hardware without measurement.

The simulator also predicts 137 total AY writes, 192 serviced T1 interrupts, and vector restoration. `tests/SIMULATED_MOCKINGBOARD_HISTORY.json` is stamped with synthetic provenance; the verifier shows that prominently.

## What this does not measure yet

- Full interrupt overhead including ROM dispatcher and RTI as one independent cycle total.
- Volume-DAC synthesis with multiple AY voices or per-voice E1 decoding inside an IRQ.
- Missed Timer 1 periods under higher combined workloads or masked IRQ intervals.
- A foreground game engine's actual sprite/HGR rendering cycle budget.
- Physical Mockingboard hardware differences and timing under different Apple II models.

The immediate acceptance goal is to confirm that **the emulator's actual AY register history** has expected 768-cycle R8 timing, expected alternating write values, and all three timer result records complete with IRQ count 64 and sensible HGR throughput. After that we can extend IRQ payload complexity and introduce a full E1 event scheduler.
