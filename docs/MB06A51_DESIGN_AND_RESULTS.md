# MB-06A.5.1 — Instrument DAC resolution trade-off study

**Reference:** MB-06A.5 v0.2, based on the 14-note MB-06A.3 `Frère Jacques` score. **CPU/score data:** generated reproducibly by `node build/build_matrix.cjs`. **Audible acceptance for 2-/4-step waveforms:** pending user listening.

## Rationale

MB-06A.4 showed that pure AY hardware-envelope saw/triangle timbres are too coarsely tuned at C4–G4. MB-06A.5 established acceptable pitch and timbre with software R8 DAC waves and with square, plucked, expressive, reed, detuned and buzzer variants. We retain all these instruments while evaluating **2, 4, 8, and 16 DAC samples per waveform period**. The composer should preserve a score's notes and rhythms while offering alternate instrument renderings, with CPU/memory suitability checked at compile time.

## What the eight variants represent

- **Software saw** (`saw2`, `saw4`, `saw8`, `saw16`): stepped rising amplitude followed by a reset. In the accepted v0.2 code the phase sample is `k % steps / steps`, so the final amplitude step is below the theoretical full-scale peak. The new two/four-step versions use the same formula intentionally to retain comparisons with the earlier 8/16-step output.
- **Software triangle** (`triangle2`, `triangle4`, `triangle8`, `triangle16`): sampled triangular amplitude profile `1 - abs(2*phase - 1)` at the same phase positions. **Triangle2 alternates two amplitudes and should sound square-like**; it does *not* have a rising and falling ramp in the mathematical sense.
- Waveform pitch is programmed using the same accurately quantized native AY tone-period frequency as the original square benchmark; actual software DAC frequency is scheduled at `period / steps`. Register events are rounded to integer CPU cycles, and identical consecutive R8 volume levels may be omitted.
- The waveform amplitude lookup uses a calibrated AYCore RMS-vs-volume curve when available, or the original nominal 16-level approximation. For a fair experiment, compare WAVs produced by the **same backend and calibration**.

## Default cost matrix — Frère Jacques, nominal volume curve

| Instrument | AY writes (all registers) | Raw E1 payload | 50-cycle write-only CPU share | Fastest nominal DAC step (G4) |
|---|---:|---:|---:|---:|
| Saw 2 | 2,301 | 9,199 B | 3.08% | 1,304 cycles |
| Saw 4 | 4,565 | 18,255 B | 6.11% | 652 cycles |
| Saw 8 | 7,965 | 31,849 B | 10.65% | 326 cycles |
| Saw 16 | 10,243 | 40,965 B | 13.70% | 163 cycles |
| Triangle 2 | 2,301 | 9,199 B | 3.08% | 1,304 cycles |
| Triangle 4 | 4,565 | 18,255 B | 6.11% | 652 cycles |
| Triangle 8 | 9,093 | 36,361 B | 12.16% | 326 cycles |
| Triangle 16 | 13,623 | 54,485 B | 18.22% | 163 cycles |

**Interpretation:** These shares are *not* measured 6502 execution. 50 cycles is a simple register-write planning assumption; native bus transfers, register selection, E1 decode, interrupt service, score streaming and HGR consume additional cycles. The fastest step value is the theoretical time between scheduled DAC updates at G4, **not** the smallest gap among all AY setup/cleanup events. The raw E1 payload excludes the 36-byte AYSB header. Actual AYCore calibration may change DAC write counts.

The v0.2 native planning model assumes 1,024 cycles per interrupt, 120 fixed cycles per IRQ, 350 cycles per E1 event, and 8 KB resident score RAM. Under those assumptions **all eight DAC variants are offline-only**; even the 2-step E1 scores exceed the 8 KB RAM cap, and their source timing is not faithfully represented by the existing 1,024-cycle scheduler. This is **not a recommendation to delete DAC instruments**. Better streaming/compression and/or sub-tick scheduling could make a subset viable.

## Composer fallback policy

Offline instrument choice is independent of musical notes and timing. Exported `MB06A51_Instrument_Substitution_Presets.json` proposes a family-preserving quality ladder, e.g.:

`triangle16 → triangle8 → triangle4 → triangle2 → saw16 → saw8 → saw4 → saw2 → square`

But quality reduction and family switching have different meanings. A change from triangle to saw changes timbre, not merely resolution; a two-step triangle is nearly a square. The final composer should default to **preserve instrument family first**, allow configurable cross-family substitutions, and expose the estimated CPU/score consequences. It must never silently change the original composition.

The current export is a **policy proposal**, not a running composer. It contains identifiers, resolution, waveform family and fallback ordering. Native capability is determined by a separate feasibility report per configuration.

## Listening and measured waveform inspection

The browser tool has two types of WAV: 1-second sustained C4 probes and full 14-note melodies, always generated by the **existing production AYCore** (`JS` or `WASM`, economy render profile, 22,050 Hz mono 16-bit PCM). It also supports real A/B playback and an overlaid waveform for C4 probes. The harmonic table is a windowed Fourier measurement of the rendered PCM sampled at *programmed* f0, **not** an independent peak-detected pitch measurement. Audacity verification of true frequency and spectral aliasing remains necessary. Neither an ideal synthesized waveform nor a mocked AYCore preview can certify physical hardware behavior.

## Validation and release scope

- Original ten candidate register schedules verified **byte-for-byte unchanged** from MB-06A.5 v0.2 (SHA-256 fixture prefixes in tests).
- 32/32 Node tests cover all 14 candidate E1 round trips, exact original schedule hashes, two/four-step level behavior, WAV/ZIP validity, native feasibility constraints, suggested fallback order and harmonic-analysis sanity.
- Mocked Chromium smoke test passes eight C4 probe renders, eight melody renders, A/B pair playback controls and harmonic table, all WAV/JSON ZIP and composer preset downloads, plus the unchanged five low-rate candidate AYSB exports. **Mock rendering does not establish sound quality.**
- No change to `EMU_CARD_mockingboard.js`, the 6502 resident IRQ engine, or other emulator components. No GitHub PR is opened in this version.

## Next acceptance gate

Ask the listener to compare **saw2 vs saw4 vs saw8 vs saw16** and **triangle2 vs triangle4 vs triangle8 vs triangle16** at C4 and in the same melody. Record acceptable timbre, perceived tuning, and audibly useful reduction in DAC resolution. Inspect plots in Audacity and retain the spectrum/pitch observations. Only then select which variants deserve a native high-resolution 6502 scheduler benchmark.
